# Prospect benchmark validation — 5 September 2026

Status: all six fresh comparisons and three rolling sequences are complete. WaterUI, Ferrum and Loomarr rolling builds are still running. Invalid comparison samples and earlier investigations remain identified separately.

The strongest fresh results are Ferrum and adorsys: warm jobs fell from 1564s to 530s and from 314s to 188s, respectively, with all tests passing. Ferrum paid a higher cold-build cost. Cadence showed a smaller image-layer benefit. dotCMS demonstrated supported remote Nx reuse, but its archive baseline was not a valid warm cache. WaterUI and Loomarr restored useful state without a whole-job speed win.

Six same-name BoringCache forks have published `boringcache-validation` branches. The shared orchestration is on [benchmarks/prospect-validation](https://github.com/boringcache/benchmarks/tree/prospect-validation). Every cache uses the existing `boringcache/benchmarks` workspace. No upstream comments, issues, PRs, or outreach were created. GitHub automatically opened three dependency PRs in the new forks; all were closed without comments. The organization enforces automatic security updates, so its policy remains unchanged.

Prepared branches: [WaterUI](https://github.com/boringcache/waterui/tree/boringcache-validation), [adorsys](https://github.com/boringcache/status-list-server/tree/boringcache-validation), [Ferrum Edge](https://github.com/boringcache/ferrum-edge/tree/boringcache-validation), [Cadence](https://github.com/boringcache/cadence/tree/boringcache-validation), [dotCMS](https://github.com/boringcache/core/tree/boringcache-validation), and [Loomarr](https://github.com/boringcache/loomarr/tree/boringcache-validation). Five contain only cache configuration. Loomarr also adds an opt-in wrapper at its existing Gradle invocation, documentation and CI-impact coverage. Exact commits are in [sources.json](sources.json); commands, job links and timing boundaries are in [results.json](results.json).

## Authentication and method

Released CLI v1.20.3 successfully enrolled GitHub OIDC on the [WaterUI fork](https://github.com/boringcache/waterui/actions/runs/33970798955) and [shared harness](https://github.com/boringcache/benchmarks/actions/runs/33973917111). Real Cadence publication and fresh-runner restore then succeeded. The adorsys build also renewed its short-lived session during compilation. No static BoringCache token was created. This proves trusted jobs hosted in our fork and shared harness; untrusted fork pull-request publication is outside the proof.

CLI selection comes from the pinned [One v1.20.2 distribution](https://github.com/boringcache/one/tree/c62af42c5c1e29388ceeea77b6a7f1db51f641e7), whose actual shipped interface was reviewed. The CLI's public `ci run` broker wraps each native adapter invocation. Runtime installation uses the standard pinned mise Action. Exact product versions are retained with artifacts.

The Rust cases run `boringcache cargo` directly on hosted Ubuntu runners; Docker is used only for Cadence. Reviewed current [Zed Cargo wiring](https://github.com/boringcache/benchmark-zed/blob/19c2b8b939628d3838ed4327bf07146b5689714d/.github/workflows/zed-cargo-product.yml) and [Deno Cargo wiring](https://github.com/boringcache/benchmark-deno/blob/665fcb2f1453120c9d5429d8f481ce25e67e888d/.github/workflows/deno-cargo-product.yml) confirm the native Cargo lifecycle, pinned upstream build inputs and strict publication/restore boundaries. Zed's current layer matrix additionally separates target-only, compiler-only and combined reuse on adjacent commits. These prospect trials use the combined Cargo path. The paired fresh trials measure same-commit reuse; the separate rolling sequences below measure successive real commits. Neither isolates the contribution of each Cargo layer or proves cross-lane sharing.

Each fresh comparison pins one source commit and uses separate standard Ubuntu 24.04 x64 GitHub runners for cold and exactly one dependent warm job. Setup and workload are identical within a case. The warm BoringCache adapter is read-only. GitHub cache keys include the run ID and attempt. The BoringCache project/lane tags were unseeded at the initial cold build. This is one observed pair per provider, not a statistical distribution.

`measured_command_seconds` includes the BoringCache adapter lifecycle. GitHub Actions archive restore/save steps sit outside its measured command; those times and full job timestamps are retained separately. Docker's cache import/export is inside both measured commands. Compare whole-job or cache-inclusive totals, never a bare archive-provider compile time against a complete BoringCache invocation. Setup, runner/network variance and artifact upload also affect whole-job durations.

## Completed evidence

Cadence: [run 33973996120](https://github.com/boringcache/benchmarks/actions/runs/33973996120) completed all four jobs. BoringCache command cold/warm: **100.785s / 58.500s**, whole jobs **113s / 69s**. GitHub GHA cache command cold/warm: **169.818s / 66.196s**, whole jobs **189s / 88s**. BoringCache warm imported a 19-layer graph, every Dockerfile build step was cached, and product evidence reports remote blob reads, zero errors and zero writes. Its warm image export/load still took about 53.4s. This is a modest warm-run difference and a larger cold export difference in one pair, not a claim about all 18 test jobs or in-container Go compilation.

dotCMS: [run 33973996156](https://github.com/boringcache/benchmarks/actions/runs/33973996156) completed all four jobs. BoringCache cold/warm commands: **187.083s / 17.505s**. Nx reported **18 of 19 tasks restored**, while BoringCache reported 18 hits, no misses, no errors and no warm writes. The GitHub archive warm command took 198.253s, but Nx emitted **Unrecognized Cache Artifacts** and rebuilt. **Exclude that row from a warm-provider speedup claim.** The pinned [Nx 23.1.1 database implementation](https://github.com/nrwl/nx/blob/23.1.1/packages/nx/src/native/db/mod.rs) keys metadata by machine ID; its [cache validation](https://github.com/nrwl/nx/blob/23.1.1/packages/nx/src/tasks-runner/cache.ts) requires matching metadata. We did not disable these checks. [Nx's explanation](https://nx.dev/docs/kb/unknown-local-cache) supports using a supported remote-cache interface for cross-machine reuse.

adorsys: [run 33973996178](https://github.com/boringcache/benchmarks/actions/runs/33973996178) completed all four jobs, each with **324 passed / 0 skipped**. BoringCache cold/warm commands: **721.765s / 148.734s**, whole jobs **761s / 188s**. GitHub cold/warm commands: **736.356s / 269.730s**, with separate cache action costs of **24s / 12s**, whole jobs **803s / 314s**. The warm BoringCache runner restored the 8.28 GB logical target snapshot in 29.6s and registry in 7.8s concurrently; Cargo reported 0.51s compilation, followed by 104.448s of tests. GitHub restored its valid 885,082,178-byte archive but rebuilt for 2m46s, followed by 100.954s of tests. This pair shows 40.1% less warm whole-job time with BoringCache; the difference is compatible Cargo state retention as well as backend behavior, not a claim about raw transfer speed alone. BoringCache's inventory reports 1,493,546,929 compressed target bytes and 128,843,720 registry bytes; native compiler storage is additional and not available as a per-project byte total in this inventory. The warm compiler proxy made no reads because Cargo reused the restored target state. The absent Cargo git entry is unused in this workload, not a failed required target restore.

WaterUI: [run 33973996116](https://github.com/boringcache/benchmarks/actions/runs/33973996116) passed all four jobs, including **1,735 passed / 36 upstream-profile skips**. BoringCache cold/warm commands: **2769.230s / 599.865s**, whole jobs **2839s / 679s**. GitHub commands: **2187.388s / 548.218s**, separate archive costs **67s / 66s**, whole jobs **2297s / 666s**. Warm cache-inclusive commands were 599.865s versus 614.218s; whole-job timings were close, with BoringCache 13s slower. BoringCache restored all three entries; its 34.18 GB logical target snapshot took 232.9s, while registry and git restored concurrently in 46.1s and 42.1s. Cargo still compiled for 2m00s and tests took 201.453s. The compiler proxy served 239 remote hits with no misses, errors or warm writes. **Large-state restore succeeded; no warm whole-job speed win was demonstrated.** The larger retained target state increased cold cost. Warm test execution alone varied by about 70s between providers, further limiting attribution of small timing differences.

WaterUI retention context: at **18:56 UTC**, the read-only upstream GitHub cache listing contained **9,999,758,439 bytes** across four entries: Windows tests, Windows lint, macOS suites and FFI. No Linux test entry was present. The usage-summary count differed from the listing count, so the raw responses and observation time are retained separately. This supports the availability concern in issue #328, but it is not a controlled eviction experiment. Our bounded Linux trial does not reproduce the complete platform matrix competing for GitHub capacity or demonstrate that its eviction problem is solved. A healthy warm-cache timing comparison and reliable cache availability answer different questions.

Loomarr: [run 33974184466](https://github.com/boringcache/benchmarks/actions/runs/33974184466) passed all four builds and artifact checks. BoringCache cold/warm commands: **1483.552s / 1385.726s**, whole jobs **1647s / 1564s**. GitHub commands: **1708.560s / 1316.386s**, separate archive costs **6s / 1s**, whole jobs **1911s / 1484s**. Both warm builds reported **467 actionable tasks: 308 executed, 159 from cache**. BoringCache reported 822 remote hits / 7 misses, no errors and no warm writes; its 99.2% request hit rate is not the percentage of all build work avoided. All four unsigned manifests confirm the pinned source, four ABIs, 76 native libraries and 16 KB ELF alignment. **No warm performance win:** the BoringCache job was 80s slower. This supports the upstream caution that a Gradle task cache alone does not eliminate the dominant native build.

Ferrum: [fresh comparison 33984066894](https://github.com/boringcache/benchmarks/actions/runs/33984066894) completed all four jobs, each passing **24,049 tests with 10 existing ignored tests**. BoringCache cold/warm commands: **2300.778s / 487.592s**, whole jobs **2340s / 530s**. GitHub commands: **1802.526s / 1515.430s**, external archive costs **24s / 16s**, whole jobs **1859s / 1564s**. This is **66.1% less warm whole-job time**, with a **481s higher cold whole-job cost**.

The BoringCache warm runner restored its 8.68 GB logical target in 50.9s and registry concurrently in 7.7s. Cargo then completed compilation in 0.61s, followed by 422.784s for the test command. The compiler proxy had no reads because the target was already reusable; there were no cache errors or warm writes. Its compressed target/registry payloads were **1,326,582,335 / 128,132,900 bytes**. The unused Cargo git entry was absent. GitHub successfully restored a 1,579,333,450-byte archive but rebuilt the application and seven vendored/local crates for 15m32s; its test command took 581.356s. Retained Cargo state accounts for the main compilation difference. Test-time variance also contributes to the whole-job gap, so this is not a pure cache-transfer comparison.

The adapter caches `cargo test --lib --test unit_tests --no-run`, then the harness runs the unchanged full test command. Compiler settings (`CC`, `CXX`, target directory and deterministic Rust wrapper) remain identical through compilation and tests on both providers. The cold test handoffs reused compilation in 1.53s and 1.52s, confirming that the corrected setup removed the earlier duplicate build. Initial cold compilation remained slower in this BoringCache observation: 29m18s versus 20m19s.

Two earlier Ferrum attempts are investigation-only. In [33973996106](https://github.com/boringcache/benchmarks/actions/runs/33973996106), both cold commands passed 24,049 tests with 10 existing ignored tests, but BoringCache correctly skipped target publication after the wrapped command changed the checkout. Diagnostics from [33981755862](https://github.com/boringcache/benchmarks/actions/runs/33981755862) identify the cause: compilation leaves a clean checkout, while tests create untracked `ferrum-managed-tls/`; no tracked source changes occur. Splitting publication from tests successfully saved an 8.68 GB logical target snapshot (1,324,424,341 compressed bytes). That attempt also exposed compiler-environment drift after the adapter exited, causing an extra 15m45s compilation. It was cancelled and the final comparison uses explicit compiler settings and fresh r3 tags. Prior investigation objects may remain in the shared content store; no physical-store cold-upload claim is made.

## Rolling commit validation

Each sequence starts at the third first-parent ancestor of the pinned upstream head, then applies the three real upstream deltas in order. The six forks publish a separate `boringcache-rolling-validation` branch. A seed integration commit adds only the reviewed cache wiring; every later snapshot matches its mapped upstream tree apart from those integration files. [rolling-sources.json](rolling-sources.json) records exact upstream/fork SHAs, parent SHAs, subjects and changed files.

Four serial jobs use fresh runners and the same prospect-specific `rolling-20260905` cohort. Every job restores existing state and permits publication after successful compilation/build; unchanged task entries may require no new writes. These are BoringCache-only sequences, following the existing Deno/Zed rolling method. They do not provide a rolling GitHub-versus-BoringCache ratio. Seed tags had no prior lookup state; physical objects in the shared workspace were not purged.

## Validation limits

Workflow syntax passed actionlint; measurement code passed Ruff. All fork configuration parsed. Loomarr shell syntax, shellcheck and CI-impact fixtures passed locally; its hosted Linux setup passed Android plugin tests, `go test -race ./internal/releaseverify`, and `make ci-lint` before the builds. Local full `make verify` was attempted but stopped on an agent-harness lock fixture; local release-verifier tests also encountered macOS's older GNU Make. The complete repository verification suite has not passed and is not represented by this benchmark.

Raw benchmark records, product JSONL, workload logs, GitHub job timestamps, pinned upstream issues and discussion are retained under each prospect directory. Missing metrics remain unavailable, not zero. The [public OIDC inventory run](https://github.com/boringcache/benchmarks/actions/runs/33982050792) retained workspace inventory, tool/run summaries and paginated sessions. Archive payload sizes include WaterUI target **6,384,658,918 bytes**, registry **244,793,580 bytes**, and git **269,342,070 bytes**; adorsys target/registry **1,493,546,929 / 128,843,720 bytes**; Cadence **919,498,355 bytes**. Native compiler/task entries are not returned by archive tag listing. Workspace-wide physical-object inventory is asynchronously refreshed and spans multiple cases; its timestamps are retained, and no per-project physical-storage or deduplication-savings claim is made. Session reports include both summary and event-derived rows; do not sum them as independent transfers.

For a new cold experiment, change the BoringCache cohort tags before dispatch. Re-dispatching these exact fixed-tag validation workflows is investigation-only after the initial seed. Cold means no prior cache lookup state for the declared tag; the shared content store was not purged.

Only compact report/manifests/summary data are intended for the validation branch. Full logs and native JSONL remain in this local evidence directory and in linked workflow artifacts; build targets, Docker images and Android bundles were not downloaded locally.
